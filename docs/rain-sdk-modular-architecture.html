Architecture Proposal · Rain Mobile SDK

One core, many providers.

A modular, ports-and-adapters redesign of the Rain iOS & Android SDKs so that Portal, Turnkey, and Privy each live in their own distributable module — and a client links only the one they actually use.

01The problem

Today the SDK is a single artifact that bundles every provider. As Rain adds wallet providers, that one decision compounds against every client.

A client who only needs Portal still compiles and ships Turnkey — and tomorrow Privy — even though that code is never called. The provider SDKs are a compile-time dependency of the core instead of a swappable runtime detail. Concretely, that costs us:

  • Binary bloat — every vendor SDK ships inside every app, whether used or not.
  • Dependency conflicts — multiple MPC/crypto stacks (BigInt, secp256k1, networking) coexisting in one graph is fragile and version-locked.
  • Security & compliance surface — a client's security team must audit all three providers to ship one.
  • Internal build friction — core cannot build/test in isolation because an iOS-only provider binary (PortalSwift) sits in the same scope. Our own CI inherits the coupling.
  • It worsens with N — each new provider re-taxes every existing client and lengthens every build.
Today (monolith)
core + Portal + Turnkey + Privy + all vendor deps
Proposed (Portal-only client)
core + Portal

02Design principle

Invert the dependency. The core should know what a wallet provider must do, never which provider is present.

The rule

Core defines an interface (the port) describing the capabilities Rain needs. Each provider is an adapter that implements the port and owns its vendor SDK as a private dependency. Core never imports a provider; providers depend on core.

Why it isolates deps

Because the dependency arrow points inward (provider → core, never core → provider), each vendor SDK lives only inside its adapter module. Linking an adapter pulls in its vendor SDK; omitting the adapter keeps that SDK out of the dependency graph entirely.

04The provider port

The hardest and most important design decision: the port is the lowest common denominator of what Rain needs — not the union of what every vendor offers.

Where providers diverge — Turnkey's P256 stamper, Portal's MPC ceremony, Privy's embedded keys — that complexity is hidden entirely inside the adapter. Where a provider can't do something at all, we model it explicitly with a capability set so core degrades gracefully instead of crashing.

iOS · Swift — RainCore
// Vendor-agnostic. No Portal/Turnkey/Privy imports here.
public protocol WalletProvider {
    var id: ProviderID { get }
    var capabilities: Set<Capability> { get }

    func createWallet(_ p: WalletParams) async throws -> Wallet
    func authenticate(_ s: SessionContext) async throws -> AuthResult
    func sign(_ payload: SignPayload) async throws -> Signature
}

public enum Capability {
    case export, recovery, multiChain, biometricGate
}
Android · Kotlin — rain-core
// Vendor-agnostic. No provider SDK imports here.
interface WalletProvider {
    val id: ProviderId
    val capabilities: Set<Capability>

    suspend fun createWallet(p: WalletParams): Wallet
    suspend fun authenticate(s: SessionContext): AuthResult
    suspend fun sign(payload: SignPayload): Signature
}

enum class Capability {
    EXPORT, RECOVERY, MULTI_CHAIN, BIOMETRIC_GATE
}
Design discipline

Resist widening the port to fit each new vendor. If Privy introduces a need core doesn't have, prefer an optional capability over a new required method. A bloated port re-couples everyone — the exact problem we're solving.

05Runtime registry — single-provider is just N = 1

Because some clients will run one provider and others will run several (migration, fallback, A/B), we design the registry for the multi-provider case. A single-provider app is simply the trivial instance of it.

Each adapter self-registers when present. The host app resolves a provider by ID (or by required capability). Nothing in core references a concrete provider type — adapters plug in from the outside.

iOS · app wiring
// App links only the adapters it ships.
import RainCore
import RainPortal     // ← only these two
import RainTurnkey    //   pull vendor SDKs

let rain = RainSDK(registry: [
    PortalProvider(config: .portal),
    TurnkeyProvider(config: .turnkey),
])

// resolve by id…
let w = try await rain
    .provider(.portal)
    .createWallet(params)

// …or by capability
let exporter = rain.first { $0.capabilities.contains(.export) }
Android · app wiring (Hilt/DI friendly)
// Module deps decide what's on the classpath.
val rain = RainSdk.builder()
    .register(PortalProvider(portalConfig))
    .register(TurnkeyProvider(turnkeyConfig))
    .build()

// resolve by id…
val w = rain
    .provider(ProviderId.PORTAL)
    .createWallet(params)

// …or by capability
val exporter = rain.first {
    Capability.EXPORT in it.capabilities
}

Single-provider app: register exactly one adapter and never call provider(id) with a second — the registry, capability negotiation, and DI all collapse to the trivial case with zero extra ceremony. We get the future-proofing for free without making the common path heavier.

06iOS packaging — where isolation is delivered

The architecture is necessary but not sufficient; the dependency isolation is delivered by how we distribute. On iOS, that means separate SPM packages, not just separate targets in one package.

Why separate packages, not one package with many products

If Portal/Turnkey/Privy are products inside a single Package.swift, every client still resolves (fetches) all vendor dependencies even when they link only one product. Splitting each provider into its own package means a Portal-only client's dependency graph never even mentions Turnkey — and our core team can build & test core without the iOS-only PortalSwift binary in scope.

RainCore/Package.swift
// No vendor dependencies whatsoever.
let package = Package(
  name: "RainCore",
  products: [.library(name: "RainCore",
                      targets: ["RainCore"])],
  targets: [.target(name: "RainCore")]
)
RainPortal/Package.swift
let package = Package(
  name: "RainPortal",
  products: [.library(name: "RainPortal",
                      targets: ["RainPortal"])],
  dependencies: [
    .package(url: "…/rain-core", from: "1.0.0"),
    .package(url: "…/PortalSwift", from: "4.0.0"),
  ],
  targets: [.target(name: "RainPortal",
    dependencies: ["RainCore", "PortalSwift"])]
)
Client adds only what they need
// A Portal-only app's Package.swift
dependencies: [
  .package(url: "…/rain-portal", from: "1.0.0")
  // rain-core comes transitively.
  // Turnkey & Privy never resolved.
]
CocoaPods parity (subspecs)
pod 'Rain/Core'
pod 'Rain/Portal'   # pulls PortalSwift
# pod 'Rain/Turnkey'  ← omitted = absent

Each subspec declares its own dependency, so an unselected subspec contributes nothing to the Podfile.lock graph.

07Android packaging

Separate Maven artifacts, one per module. The client's Gradle file decides what's on the classpath; an unselected provider's transitive vendor SDK never enters the dependency graph.

Published artifacts
xyz.rain:rain-core:1.x        // no vendor deps
xyz.rain:rain-portal:1.x      // api(core)+Portal
xyz.rain:rain-turnkey:1.x     // api(core)+Turnkey
xyz.rain:rain-privy:1.x       // api(core)+Privy
rain-portal/build.gradle.kts
dependencies {
  api("xyz.rain:rain-core:1.0.0")
  implementation("co.portalhq:portal-android:4.0.0")
}
// 'implementation' keeps Portal's internals
// off the consumer's compile classpath.
A Portal-only app — one line
dependencies {
  implementation("xyz.rain:rain-portal:1.0.0")
  // rain-core resolved transitively.
  // Turnkey & Privy artifacts are never fetched, compiled, or shipped.
}

R8/ProGuard would strip unused code at the end — but module separation is stronger: the dependency never enters the graph in the first place, so there is no version to resolve, no conflict to mediate, and nothing for a security audit to cover.

08Versioning & the compatibility BOM

Independent modules mean independent release cadence — but we still need a sane way to say "these versions work together."

Per-module semver
  • Each module versions independently. Ship a Privy fix without forcing a Portal client to upgrade.
  • Core defines the contract. A breaking port change is a core major bump; adapters declare the core range they support.
  • Adapters never break each other — they share nothing but core.
Bill of Materials (BOM)

Publish a rain-bom that pins a tested matrix of core + adapter versions. Clients import the BOM and omit individual versions.

// Android
implementation(platform("xyz.rain:rain-bom:2026.06"))
implementation("xyz.rain:rain-portal") // version from BOM

iOS has no native BOM; we ship a documented compatibility matrix + a verified Package.resolved reference.

09Migration path — refactor, not rewrite

This is the part that de-risks the proposal: every phase ships independently and stays backward-compatible. We are never in a broken half-state, and we never block client releases.

Extract the port in place

Define WalletProvider + capability model in the existing codebase. Make today's Portal/Turnkey code implement it. No packaging change yet, no behavior change.

Ships as today's monolith — zero client impact

Push each vendor behind its adapter

Move provider-specific code (P256 stamper, MPC ceremony) behind the adapter boundary internally. Core stops referencing vendor types directly. Still one artifact.

Internal seam only — still backward compatible

Split the build & publish

Publish rain-core + rain-portal + rain-turnkey as separate modules. The old monolith becomes a thin umbrella that re-exports them, so existing integrations keep working untouched.

New clients get modular; old clients unaffected

Onboard Privy as a net-new module

Privy arrives as rain-privy — its own artifact, its own vendor dep. The proof the architecture works: a new provider costs existing clients nothing.

Validates the whole thesis

Deprecate the umbrella

Once clients have migrated to per-provider modules, sunset the monolithic artifact on a published timeline.

End state — fully modular
Migration tooling

A migration skill will ship alongside the modular release so a coding agent can perform the move automatically. It rewrites a monolith integration to the per-provider modules — swapping the umbrella dependency for the specific rain-portal / rain-turnkey / rain-privy artifact (SPM/CocoaPods on iOS, Gradle/Maven on Android), updating imports and provider registration, and verifying the build. Clients adopt the new architecture without a manual refactor.
